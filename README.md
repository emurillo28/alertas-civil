# alertas-civil

Serverless clinical alerts backend for **Hospital Civil de Guadalajara**. Ingests lab results, evaluates critical thresholds, and fires clinician notifications — all on AWS.

---

## What it does

1. **Receives** lab results from equipment or UI → API Gateway → SQS (async, fire-and-forget)
2. **Evaluates** whether any analyte crosses a critical threshold (hemoglobin, glucose, potassium, etc.)
3. **Persists** the result in DynamoDB with the patient's full clinical timeline
4. **Notifies** the clinician via SQS → SMS / WhatsApp / Push / Email

---

## Stack

| What | How |
|------|-----|
| Language | Java 25 |
| Framework | Quarkus 3.36 (imperative mode) |
| Runtime | AWS Lambda (SQS handler + JAX-RS via API Gateway) |
| Concurrency | Virtual Threads (Project Loom) — no reactive, no Mutiny |
| Database | DynamoDB single-table (`hc-alertas`) |
| Queues | Amazon SQS (ingestion + notifications) |
| Storage | S3 (`hc-alertas-clinical-docs`) — raw lab PDFs |
| IaC | Terraform |
| Tests | JUnit 5 + Testcontainers + LocalStack |

> **No reactive.** Zero `Uni`, `Multi`, `Mono`, or callbacks. Everything is sequential and blocking — the JVM handles concurrency through virtual threads. Simpler to read, simpler to debug.

---

## Flow

```
Write (ingestion):
  [Lab / UI] → POST /labs → [API Gateway] → [SQS] → [IngestLabSqsHandler] → [DynamoDB]

Read (query):
  [UI] → GET /labs/patients/... → [API Gateway] → [Lambda / Quarkus] → [DynamoDB]

Notify (alert):
  [UI] → POST /labs/{id}/notify → [Quarkus] → [SQS] → downstream push/SMS
```

---

## Endpoints

| Method | Path | What it does |
|--------|------|--------------|
| `POST` | `/api/v1/labs` | Ingest a lab result (via SQS, async) — `labId` is client-generated |
| `GET` | `/labs/patients` | List registered patients |
| `GET` | `/labs/patients/{patientId}/latest` | Most recent result for a patient |
| `GET` | `/labs/patients/{patientId}/history` | Full clinical timeline |
| `POST` | `/labs/{labId}/notify` | Trigger a clinician notification |

> Ingestion goes straight to SQS — API Gateway never hits Lambda on that path. Reads go through Quarkus/Lambda.
>
> The `labId` is generated by the client before the POST — it can come from the legacy system or be a UUID v4 generated on the frontend. The backend never creates it.

## Critical thresholds

The backend auto-evaluates `criticalAlert` on every ingestion:

| Analyte | Critical low | Critical high |
|---------|-------------|---------------|
| Hemoglobin | < 7.0 g/dL | > 20.0 g/dL |
| Glucose | < 50.0 mg/dL | > 400.0 mg/dL |
| Potassium | < 2.5 mmol/L | > 6.0 mmol/L |
| Sodium | < 120.0 mmol/L | > 160.0 mmol/L |
| Creatinine | — | > 10.0 mg/dL |
| Platelets | < 50.0 ×10³/µL | > 1000.0 ×10³/µL |

Keys are matched case-insensitively — `Hemoglobin`, `hemoglobina`, and `HEMOGLOBIN` all work.

## DynamoDB — single table `hc-alertas`

Everything lives in one table:

| Item | PK | SK |
|------|----|----|
| Patient profile | `PATIENT#<id>` | `METADATA` |
| Lab result | `PATIENT#<id>` | `LAB#<labId>` |

A single query by `PK` returns the patient profile + full lab history in one round-trip.

Each item carries a `Version` number enabling **Optimistic Concurrency Control (OCC)** — every write has a `ConditionExpression` on `Version` to prevent concurrent conflicts.
